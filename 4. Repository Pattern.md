অবশ্যই। 🔥 এবার **Repository Pattern**। এটা তোমার জন্য বিশেষভাবে গুরুত্বপূর্ণ, কারণ Laravel, Spring Boot, NestJS—সব ecosystem-এ এই concept বারবার দেখতে পাবে।

আমরা আগের মতোই করব:

**গল্প → সংজ্ঞা → সমস্যা → Pseudo Code → Raw JS → DI-এর সাথে connection → Real Backend Architecture → কখন ব্যবহার করবে → Cheat Sheet**

# Design Pattern #4 — Repository Pattern

## 1. আগে গল্প দিয়ে বুঝি

ধরো তুমি একটা **E-commerce application** বানাচ্ছ।

তোমার `UserService`-এর কাজ:

```text
User registration
User login
User profile
User search
```

একদিন `UserService`-এর মধ্যে database query লিখলে:

```text id="4njf0c"
CLASS UserService

    FUNCTION getUser(id)

        SQL:
        SELECT * FROM users WHERE id = id

    END

END
```

শুরুতে ঠিক আছে।

কিন্তু কিছুদিন পর:

```text id="3qz4z7"
UserService
    ↓
SQL Query
    ↓
MySQL
```

এখন UserService-এর মধ্যে:

```text id="bd7c4x"
SELECT
INSERT
UPDATE
DELETE
JOIN
Transaction
Pagination
Filtering
```

সব ঢুকে যাচ্ছে।

তখন Service-এর আসল business logic আর database logic একসাথে মিশে যাচ্ছে।

**Repository Pattern এই সমস্যাটা solve করে।**

---

# 2. Repository Pattern-এর সংজ্ঞা

সহজ ভাষায়:

> **Repository Pattern হলো এমন একটি abstraction layer যা application-এর business logic এবং data source/database-এর মাঝখানে অবস্থান করে এবং data access-এর দায়িত্ব নেয়।**

Architecture:

```text id="lhggl2"
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

Repository-এর কাজ:

```text id="x1q4zv"
"Data কোথা থেকে আসছে সেটা আমি handle করব।"
```

Service-এর কাজ:

```text id="1v9m2a"
"Business rule আমি handle করব।"
```

---

# 3. Dependency Injection-এর সাথে পার্থক্য

এখানে একটা গুরুত্বপূর্ণ বিষয়।

**DI হলো technique।**

**Repository হলো architectural pattern।**

যেমন:

```text id="4t6wnb"
DI
→ dependency বাইরে থেকে দেওয়া

Repository
→ data access আলাদা করা
```

Repository-কে আবার DI দিয়ে Service-এর মধ্যে inject করা যায়।

# 6. প্রথম Repository Pseudo Code

Repository:

```text id="mnh6af"

    FUNCTION findById(id)

        RETURN DATABASE.query(
            "SELECT * FROM users WHERE id = ?",
            id
        )

    END

END
```

Service:

```text id="3u0ddg"
CLASS UserService

    FUNCTION constructor(userRepository)

        THIS.userRepository = userRepository

    END


    FUNCTION getUser(id)

        RETURN THIS.userRepository.findById(id)

    END

END
```

এখানে খুব সুন্দর separation:

```text id="5rh5uw"

    ↓

UserRepository
    ↓
Data Access
```

# 17. Service-এর কাজ কী?

এখানে একটা খুব গুরুত্বপূর্ণ separation শিখে রাখো।

ধরো user registration:

```text id="lppp6q"
Controller
    ↓
register()
    ↓
UserService
    ↓
Business Rules
    ↓
UserRepository
    ↓
Database
```

Service:

```js id="m0k2ud"
class UserService {

    constructor(userRepository) {
        this.userRepository = userRepository;
    }

    register(data) {

        const existingUser =
            this.userRepository
                .findByEmail(data.email);

        if (existingUser) {
            throw new Error(
                "Email already exists"
            );
        }

        // business logic

        return this.userRepository
            .create(data);
    }
}
```

এখানে:

```text id="gqwb1y"
UserService
    ↓
"Email already exists?"
```

এটা **business rule**।

আর:

```text id="q9x3yf"
UserRepository
    ↓
SELECT ...
```

এটা **data access**।

# 21. এবার Interface / Contract-এর Concept

```text id="n9xjgr"

      ↑
```



```text id="k4o4qv"

    IMPLEMENTS UserRepository

    findById(id)
        ...
    END

END
```

Service:

```text id="h3y1m8"

    constructor(userRepository)

        this.userRepository =
            userRepository

    END

END
```

## চারটা Pattern এখন একসাথে মনে রাখো

| Pattern        | মূল প্রশ্ন                   |
| -------------- | ---------------------------- |
| **DI**         | Dependency কীভাবে আসবে?      |
| **Factory**    | কোন object তৈরি হবে?         |
| **Strategy**   | কোন behavior/algorithm চলবে? |
| **Repository** | Data access কোথায় থাকবে?     |

আর পুরো backend-এর mental model:

```text id="q5g0pj"
                    REQUEST
                       ↓
                  CONTROLLER
                       ↓
                    SERVICE
                   ↙       ↘
              STRATEGY    REPOSITORY
                 ↓            ↓
             BEHAVIOR      DATABASE
                 
       ↑
    FACTORY
       │
  creates/selects
    Strategy

       ↑
      DI
       │
injects dependencies
```

**একটা জিনিস খুব ভালোভাবে বুঝে রাখো:** Repository Pattern-এর উদ্দেশ্য শুধু `UserRepository` বানানো না। আসল উদ্দেশ্য হলো **business logic-কে persistence/data-access concerns থেকে আলাদা করা**। এটা বুঝে গেলে Laravel-এর Eloquent, Spring Data JPA, Prisma/Sequelize—সবকিছুর architecture অনেক সহজে বুঝতে পারবে।
