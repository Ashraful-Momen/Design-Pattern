অবশ্যই 🔥 এবার **Singleton Pattern**। এটা একটু tricky pattern, কারণ এটা দেখতে খুব simple হলেও **কখন ব্যবহার করা উচিত এবং কখন ব্যবহার করা উচিত না**—এই জায়গাটাই Backend Engineer হিসেবে সবচেয়ে গুরুত্বপূর্ণ।

আমরা আগের sequence-এই যাব:

**গল্প → সংজ্ঞা → সমস্যা → Pseudo Code → Raw JS → Backend Example → DI-এর সাথে সম্পর্ক → সমস্যা/সতর্কতা → Cheat Sheet**

# Design Pattern #8 — Singleton Pattern

## 1. আগে গল্প দিয়ে বুঝি

ধরো তোমার একটা অফিসে **একটা Security Control Room** আছে।

পুরো অফিসের জন্য:

```text
Security Control Room
```

একটাই।

যে department-ই security information চাইবে:

```text
HR
 ↓
Security Room

Accounts
 ↓
Security Room

IT
 ↓
Security Room
```

কিন্তু কেউ নতুন Security Room বানাতে পারবে না।

অর্থাৎ:

```text
পুরো application
       ↓
একটাই instance
```

এটাই Singleton-এর মূল idea।

---

# 2. Singleton Pattern-এর সংজ্ঞা

> **Singleton Pattern হলো একটি creational design pattern যা নিশ্চিত করে যে কোনো class-এর application lifecycle-এর নির্দিষ্ট scope-এ সর্বোচ্চ একটি instance থাকবে এবং সেই instance-এ access করার একটি global entry point থাকবে।**

সহজ ভাষায়:

> **একটা class → একটা instance → সবাই সেই একই instance ব্যবহার করবে।**

Mental model:

```text
Class
  ↓
ONE INSTANCE
  ↓
সবাই একই instance ব্যবহার করছে
```

---

# 3. Singleton কেন দরকার?

ধরো তোমার application-এ একটা configuration manager আছে:

```text
APP_ENV
DATABASE_URL
API_KEY
LOG_LEVEL
```

তুমি যদি বারবার:

```js
new Config()
```

করো:

```text
Config #1
Config #2
Config #3
Config #4
```

তাহলে unnecessary multiple instances তৈরি হচ্ছে।

আমরা চাই:

```text
Config
   ↓
ONE INSTANCE
   ↑
   │
সবাই একইটা ব্যবহার করবে
```

---

# 4. প্রথমে Problem

Normal class:

```js
class Config {

    constructor() {
        console.log("Config created");
    }
}
```

এখন:

```js
const config1 = new Config();
const config2 = new Config();
const config3 = new Config();
```

Output:

```text
Config created
Config created
Config created
```

তিনটা object তৈরি হয়েছে।

```text
config1 !== config2
config2 !== config3
```

---

# 5. আমরা কী চাই?

```js
const config1 = Config.getInstance();
const config2 = Config.getInstance();
```

এখন:

```js
config1 === config2
```

অর্থাৎ:

```text
config1
   ↓
 ┌──────────┐
 │  Config  │
 └──────────┘
   ↑
config2
```

দুজন একই object-এর reference ধরে রেখেছে।

# 6. Pseudo Code

প্রথমে concept:

```text
CLASS Config

    PRIVATE static instance


    PRIVATE constructor()

        load configuration

    END


    STATIC FUNCTION getInstance()

        IF instance does not exist

            instance =
                NEW Config()

        END IF

        RETURN instance

    END

END
```

এখানে সবচেয়ে গুরুত্বপূর্ণ:

```text
IF instance doesn't exist
    create
ELSE
    return existing
```

---

# 7. Raw JavaScript

```js
class Config {

    static instance = null;

    constructor() {

        if (Config.instance) {
            return Config.instance;
        }

        console.log("Config created");

        this.appName = "My App";
        this.environment = "production";

        Config.instance = this;
    }

    static getInstance() {

        if (!Config.instance) {
            Config.instance = new Config();
        }

        return Config.instance;
    }
}
```

ব্যবহার:

```js
const config1 =
    Config.getInstance();

const config2 =
    Config.getInstance();
```

তারপর:

```js
console.log(config1 === config2);
```

Output:

```text
true
```

# 8. আরও Simple JavaScript Singleton

JavaScript-এ module system থাকার কারণে অনেক সময় আরও simple approach ব্যবহার করা যায়।

```js
class Config {

    constructor() {

        this.appName = "My App";
        this.env = "production";
    }
}

const config =
    new Config();

export default config;
```

যেখানে দরকার:

```js
import config from "./config.js";
```

সব জায়গায় একই exported object ব্যবহার হবে।

এটাও JavaScript ecosystem-এ Singleton-like pattern হিসেবে খুব common।

# 9. Singleton-এর আসল Concept

এখানে একটা বিষয় খুব ভালোভাবে বুঝো:

Singleton মানে:

```text
"Class-এর object একটাই"
```

না।

আরও precise definition:

> **একটি নির্দিষ্ট scope/lifecycle-এর মধ্যে একটি shared instance।**

এই scope গুরুত্বপূর্ণ।

যেমন:

```text
Application
   ↓
ONE Config instance
```

কিন্তু distributed system-এ:

```text
Server 1 → Config instance
Server 2 → Config instance
Server 3 → Config instance
```

প্রতিটা process-এর নিজের instance থাকতে পারে।

তাই Singleton **globally across all servers** automatically একটাই object তৈরি করে না।

```js
const logger1 =
```

```js

```

দুজন একই Logger instance ব্যবহার করছে।

# 11. Database Connection Example

ধরো:

```text
Application
   ↓
Database Connection
```

Database connection object বারবার create করা unnecessary হতে পারে।

Conceptually:

```text
DatabaseConnection
        ↓
   ONE INSTANCE
        ↑
   ┌────┼────┐
   ↓    ↓    ↓
Service A
Service B
Service C
```

Raw JS:

```js
class Database {

    static instance = null;

    constructor() {

        if (Database.instance) {
            return Database.instance;
        }

        console.log(
            "Creating database connection"
        );

        this.connection =
            "DATABASE CONNECTION";

        Database.instance = this;
    }

    static getInstance() {

        if (!Database.instance) {
            Database.instance =
                new Database();
        }

        return Database.instance;
    }
}
```

তারপর:

```js
const db1 =
    Database.getInstance();

const db2 =
    Database.getInstance();

console.log(db1 === db2);
```

```text
true
```

# 12. কিন্তু এখানে একটা গুরুত্বপূর্ণ বিষয় ⚠️

বাস্তব backend framework-এ database connection-এর ক্ষেত্রে **নিজে হাতে Singleton বানানো সবসময় best practice নয়**।

কারণ:

```text
Laravel
Spring
NestJS
```

এর মতো framework/container সাধারণত lifecycle এবং dependency management handle করতে পারে।

তাই concept বুঝবে:

```text
"একটা shared database connection/resource"
```

কিন্তু production code-এ framework-এর connection pool/container ব্যবহার করা সাধারণত ভালো।

```text

   ↓
```

# 14. Singleton আর DI একই জিনিস নয়

এটা খুব ভালোভাবে মনে রাখবে।

### Singleton

প্রশ্ন:

> **"একটা instance-ই থাকবে কীভাবে?"**

### DI

প্রশ্ন:

> **"Dependency object-টা class-এর কাছে কীভাবে পৌঁছাবে?"**

দুটো আলাদা concept।


# 16. Singleton + Repository

ধরো:

```text
UserRepository
```

তুমি চাইলে এটাকে Singleton করতে পারো।

> **এটা কি সত্যিই দরকার?**


# 19. Singleton + State

এখানে আসল danger শুরু হয়।

ধরো Singleton:

```js
class AppState {

    static instance;

    constructor() {

        this.user = null;
    }

    static getInstance() {

        if (!this.instance) {
            this.instance =
                new AppState();
        }

        return this.instance;
    }
}
```

এক জায়গায়:

```js
const state =
    AppState.getInstance();

state.user = "Rahim";
```

অন্য জায়গায়:

```js
const state =
    AppState.getInstance();

console.log(state.user);
```

Output:

```text
Rahim
```

কারণ shared state।

কিন্তু backend-এ shared mutable state dangerous হতে পারে।

# 20. কেন Singleton কখনও Dangerous?

কারণ এটা effectively global shared state তৈরি করতে পারে।

```text
Service A
   ↓
   Singleton
   ↑
Service B
```

Service A state পরিবর্তন করলে:

```text
Service B
```

সেটা দেখতে পারে।

এতে:

```text
Hidden Dependency
Global State
Testing Difficulty
Concurrency Issues
```

হতে পারে।

# 21. Testing Problem

ধরো:

```js
const cache =
    Cache.getInstance();

cache.set(
    "user",
    "Rahim"
);
```

Test 1 শেষ হওয়ার পর cache clear হলো না।

Test 2 শুরু হলো:

```js
const cache =
    Cache.getInstance();
```

আগের test-এর state এখনও থাকতে পারে।

তখন:

```text
Test 1
  ↓
Singleton state
  ↓
Test 2
```

Test isolation নষ্ট হতে পারে।

# 22. তাই Singleton blindly ব্যবহার করবে না

এই প্রশ্নগুলো করো:

```text id="f2x9c7"
এই resource কি সত্যিই shared হওয়া দরকার?
             ↓
            YES
             ↓
একটাই instance দরকার?
             ↓
            YES
             ↓
Framework কি lifecycle manage করতে পারে?
             ↓
            YES
             ↓
Framework DI/container ব্যবহার করো
```

# 23. Singleton কোথায় ভালো?

যেসব object-এর state/application-wide sharing যৌক্তিক হতে পারে:

```text
Configuration
Logger
Metrics Registry
Certain Cache Manager
Application-wide immutable services
Resource managers
```

তবে framework-এর lifecycle management থাকলে সেটাই prefer করবে।

---

# 24. Singleton কোথায় Avoid করবে?

বিশেষ করে:

```text
Request-specific data
User-specific state
Mutable business state
Temporary transaction state
```

যেমন:

```text
currentUser
currentOrder
requestData
authentication state
```

এসব global Singleton-এ রাখা risky।

# 25. একটা খুব গুরুত্বপূর্ণ Backend Example

ধরো:

```text
User A
Request A
   ↓
Singleton
```

তারপর:

```text
User B
Request B
   ↓
same Singleton
```

যদি Singleton-এর মধ্যে user-specific state রাখো:


তাহলে request isolation সমস্যা হতে পারে।

Backend-এ request-specific data সাধারণত request scope/context-এ রাখা উচিত, global Singleton-এ নয়।

# 28. Singleton-এর Real Mental Model

যখন তুমি problem দেখবে:

```text
আমার application-এ এই resource-এর
একটা shared instance দরকার।
```

তখন Singleton চিন্তা করবে।

```text
          Class
            ↓
       getInstance()
            ↓
      ┌───────────┐
      │  Object   │
      └───────────┘
        ↑   ↑   ↑
        │   │   │
       A    B   C
```

A, B, C সবাই একই object ব্যবহার করছে।

---

# 29. Singleton-এর Lifecycle

একদম সহজ:

```text
First Request
     ↓
Instance আছে?
     ↓
    NO
     ↓
Create Instance
     ↓
Return

Second Request
     ↓
Instance আছে?
     ↓
    YES
     ↓
Return Existing Instance
```

Pseudo code:

```text
FUNCTION getInstance()

    IF instance == null

        instance = NEW Object()

    END IF

    RETURN instance

END
```

এই logic-টাই Singleton-এর heart।

# 30. Advanced Concept — Lazy Initialization

আমাদের example:

```js
Config.getInstance();
```

call না করা পর্যন্ত object তৈরি হচ্ছে না।

এটা:

> **Lazy Initialization**

```text
Application Start
       ↓
No Config Object

First getInstance()
       ↓
Create

Next getInstance()
       ↓
Reuse
```

এটা resource creation defer করতে সাহায্য করতে পারে।

# 32. Laravel/Spring-এ Important Connection

তুমি যেহেতু Laravel + Spring Boot শিখছ, এটা বিশেষভাবে মনে রাখো।

তুমি manually:

```text
Singleton Pattern
```

implement না করেও framework-এর **Dependency Injection Container / Bean lifecycle** দিয়ে shared instance পেতে পারো।

```text
Application Container
        ↓
One Service Instance
        ↓
Inject wherever needed
```

অর্থাৎ framework অনেক সময় Singleton-এর **lifecycle management** তোমার হয়ে করে দেয়।

Laravel-এর container-এও singleton binding করা যায়।

এজন্য raw pattern বুঝে তারপর framework implementation শেখা সবচেয়ে ভালো approach।

```text id="z3q8m1"
      └── Shared mutable state
```

# 🔥 এখন ৮টা Pattern-এর Mental Map

| Pattern        | মূল প্রশ্ন                                   |
| -------------- | -------------------------------------------- |
| **DI**         | Dependency কীভাবে আসবে?                      |
| **Factory**    | কোন Object তৈরি হবে?                         |
| **Builder**    | Complex Object কীভাবে তৈরি হবে?              |
| **Singleton**  | Object-এর একটাই shared instance কীভাবে রাখব? |
| **Strategy**   | কোন Behavior/Algorithm চলবে?                 |
| **Repository** | Data Access কোথায় থাকবে?                     |
| **Adapter**    | Incompatible Interface কীভাবে মিলবে?         |
| **Facade**     | Complex subsystem কীভাবে সহজ হবে?            |

### Singleton এক লাইনে:

> **Singleton = একটি নির্দিষ্ট application scope-এ একটি shared instance নিশ্চিত করা।**

আর সবচেয়ে গুরুত্বপূর্ণ distinction:

```text
Singleton
    ↓
ONE INSTANCE

DI
    ↓
HOW DEPENDENCY IS PROVIDED

Factory
    ↓
WHICH OBJECT TO CREATE

Builder
    ↓
HOW TO BUILD COMPLEX OBJECT
```

**Backend Engineer হিসেবে Singleton-এর code মুখস্থ করার চেয়ে এর limitation বোঝা বেশি গুরুত্বপূর্ণ।** বিশেষ করে modern Laravel/Spring/Node architecture-এ **"নিজে Singleton বানাব"** বলার আগে ভাববে—**DI container কি এই lifecycle ইতিমধ্যে manage করছে?** 🔥
