অবশ্যই। DI-এর মতোই **Factory Pattern-ও framework-independent** ভাবে শিখব—আগে গল্প, তারপর সংজ্ঞা, সমস্যা, pseudo code, simple Raw JS, তারপর backend example এবং শেষে framework-এ কীভাবে চিনবে।

Factory হলো **Creational Design Pattern**—মূল উদ্দেশ্য হলো object তৈরির logic-কে ব্যবহার করার জায়গা থেকে আলাদা করা। ([Baeldung on Kotlin][1])

# Design Pattern #2 — Factory Pattern

## 1. আগে একটা গল্প

ধরো তুমি একটা **Payment System** বানাচ্ছ।

তোমার application-এ তিন ধরনের payment আছে:

```text
bKash
Nagad
Card
```

তুমি যদি সরাসরি Controller-এ object তৈরি করো:

```text
IF paymentType == "bkash"
    payment = NEW BkashPayment()

ELSE IF paymentType == "nagad"
    payment = NEW NagadPayment()

ELSE IF paymentType == "card"
    payment = NEW CardPayment()
```

শুরুতে সমস্যা নেই।

কিন্তু project বড় হলে?

```text
Controller
    ↓
কোন Payment class বানাতে হবে
    ↓
if/else
    ↓
new BkashPayment()
new NagadPayment()
new CardPayment()
```

তখন object creation-এর logic ছড়িয়ে যেতে থাকে।

**Factory-এর কাজ হলো এই creation decision-টাকে একটা জায়গায় নিয়ে যাওয়া।**

---

# 2. Factory Pattern-এর সংজ্ঞা

সহজ ভাষায়:

> **Factory Pattern হলো এমন একটি design pattern যেখানে object তৈরির logic আলাদা একটি component-এর মধ্যে রাখা হয়, যাতে client-কে concrete class কীভাবে তৈরি হচ্ছে সেটা জানতে না হয়।**

অর্থাৎ:

```text
আগে:

Controller
   ↓
new BkashPayment()
new NagadPayment()
new CardPayment()


Factory-এর পরে:

Controller
   ↓
PaymentFactory
   ↓
কোন object তৈরি করতে হবে?
   ↓
Bkash / Nagad / Card
```

Factory মূলত **object creation-এর দায়িত্ব নেয়**। ([Baeldung on Kotlin][1])

এবং application নিজেই object তৈরি করছে।

# 5. Factory কী করবে?

আমরা বলব:

> "Application, তুমি object বানানোর চিন্তা করো না। Factory-কে বলো কোন type চাই।"

```text
Application
     │
     │ "I need bkash"
     ↓
PaymentFactory
     │
     │ creates
     ↓
BkashPayment
```

# 6. প্রথম Factory Pseudocode

```text
CLASS PaymentFactory

    FUNCTION create(type)

        IF type == "bkash"

            RETURN NEW BkashPayment()

        ELSE IF type == "nagad"

            RETURN NEW NagadPayment()

        ELSE IF type == "card"

            RETURN NEW CardPayment()

        END IF

    END

END
```

এখন Application:

```text
payment =
    PaymentFactory.create("bkash")

payment.pay(1000)
```

Application আর জানে না:

```text
NEW BkashPayment()
```

কোথায় হচ্ছে।

# 7. সবচেয়ে গুরুত্বপূর্ণ Concept

Factory-এর core idea:

```text
BEFORE

Client
  ↓
creates object


AFTER

Client
  ↓
asks Factory
  ↓
Factory creates object
```

মনে রাখো:

> **Factory = Object Creation-এর দায়িত্ব আলাদা করা।**

# 13. এবার DI + Factory একসাথে

এখানেই আগের lesson-এর সাথে connection।

ধরো:

```text
PaymentService
       ↓
PaymentFactory
```

Pseudo code:

```text
CLASS PaymentService

    constructor(paymentFactory)

        THIS.paymentFactory =
            paymentFactory

    END

    FUNCTION pay(type, amount)

        payment =
            THIS.paymentFactory.create(type)

        RETURN payment.pay(amount)

    END

END
```

Application:

```text
factory =
    NEW PaymentFactory()

    NEW PaymentService(factory)
```

এখানে:

```text
DI
↓
PaymentFactory injected
```

আর:

```text
Factory
↓
Payment object created
```

দুইটা pattern একসাথে কাজ করছে।

# 17. এখন একটা Real Backend Example

ধরো তোমার ERP system-এ notification দিতে হবে।

Notification types:

```text
Email
SMS
Push
WhatsApp
```

Factory ছাড়া:

```text
CLASS NotificationService

    FUNCTION send(type, message)

        IF type == "email"

            notification =
                NEW EmailNotification()

        ELSE IF type == "sms"

            notification =
                NEW SMSNotification()

        ELSE IF type == "push"

            notification =
                NEW PushNotification()

        END IF

        notification.send(message)

    END

END
```

Factory দিয়ে:

```text
NotificationService
        ↓
NotificationFactory
        ↓
Email / SMS / Push / WhatsApp
```

Service:

```text
CLASS NotificationService

    constructor(factory)

        THIS.factory = factory

    END

    FUNCTION send(type, message)

        notification =
            THIS.factory.create(type)

        notification.send(message)

    END

END
```

এটা অনেক cleaner।

# 19. Factory কখন ব্যবহার করবে?

এসব ক্ষেত্রে Factory খুব natural fit।

# 20. কিন্তু একটা গুরুত্বপূর্ণ সতর্কতা ⚠️

```text
     ↓

```

```text

storageType
reportType
```

অর্থাৎ **object creation-এর decision/complexity** আছে।

# 21. Factory-এর আরেকটা সুন্দর Version

আমাদের `if/else` অনেক বড় হয়ে গেলে map ব্যবহার করতে পারি:

```js
class PaymentFactory {

    create(type) {

        const payments = {
            bkash: BkashPayment,
            nagad: NagadPayment,
            card: CardPayment
        };

        const Payment =
            payments[type];

        if (!Payment) {
            throw new Error(
                "Unsupported payment type"
            );
        }

        return new Payment();
    }
}
```

এখন নতুন payment:

```js
rocket: RocketPayment
```

যোগ করা সহজ।

# 22. Factory Method বনাম Simple Factory

এখানে একটা terminology বিষয় আছে।

আমরা এখন যেটা শিখলাম:

```text
PaymentFactory.create(type)
```

এটাকে অনেক practical codebase-এ **Simple Factory** বলা হয়।

আর GoF-এর classic **Factory Method** আরও নির্দিষ্ট pattern—creation method-টি subclass override করে concrete product তৈরির সিদ্ধান্ত নেয়। ([GeeksforGeeks][2])

তাই এখনই দুটো গুলিয়ে ফেলবে না।

আমাদের বর্তমান লক্ষ্য:

```text
Factory-এর CORE IDEA
=
Object creation আলাদা করা
```

তারপর advanced level-এ:

```text
Simple Factory
       ↓
Factory Method
       ↓
Abstract Factory
```

শিখবে।

# 24. Abstract Factory পরে কেন লাগবে?

ধরো শুধু একটা object না, **related family of objects** তৈরি করতে হবে।

যেমন UI system:

```text
Windows
 ├── Button
 ├── Checkbox
 └── Dialog

Mac
 ├── Button
 ├── Checkbox
 └── Dialog
```

তখন:

```text
Abstract Factory
```

useful হতে পারে। Abstract Factory related/dependent object-এর family তৈরি করার জন্য ব্যবহৃত হয়। ([Wikipedia][3])

এটা এখন তোমার শেখার দরকার নেই; Factory core ভালোভাবে বুঝে পরে করব।

# 🧠 Factory Pattern — Final Cheat Sheet

```text
FACTORY PATTERN
│
├── Category
│     └── Creational
│
├── Main Problem
│     └── Object creation logic becomes messy
│
├── Solution
│     └── Move creation logic to Factory
│
├── Input
│     └── type/configuration
│
├── Output
│     └── required object
│
├── Main Benefit
│     ├── Loose Coupling
│     ├── Cleaner Code
│     ├── Centralized Creation
│     └── Easier Extension
│
└── Common Examples
      ├── Payment
      ├── Notification
      ├── Storage
      ├── Parser
      ├── Report
      └── Database Driver
```
